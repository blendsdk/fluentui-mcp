# TableCellActions

> **Package**: `@fluentui/react-table` v9.19.16
> **Import**: `import { TableCellActions } from '@fluentui/react-components';`
> **Category**: data-display
> **Stability**: stable

## Overview

TableCellActions is a lightweight layout component for the Fluent UI React v9 Table family that hosts the interactive controls belonging to a single row — typically icon-only Buttons, CompoundButtons, Menu triggers, or ToolbarButtons. It renders a single root slot element (a container div rendered inside a TableCell) whose sole job is to group and position those controls at the trailing edge of a row so they appear when the user hovers or focuses the row, and hide again when attention moves elsewhere. Because it occupies a cell rather than overlaying the table, the actions participate in normal table layout and grid semantics instead of floating above content. The component exposes exactly one prop, visible, which forces the actions into their always-shown state — the standard technique for keeping a row's actions pinned open while a Popover, Menu, or Dialog launched from that row is still open. TableCellActions ships unstyled beyond a small spacing/alignment wrapper, so the visual weight of the row actions comes entirely from the Button or Menu components you place inside it.

**When to use**: Use TableCellActions when each row of a Table or DataGrid needs its own set of secondary controls — edit, delete, share, "more options" — that should stay out of the way until the user engages with that row. It is the right choice for trailing-edge row affordances that belong to one record at a time. Reach for a persistent Toolbar when the controls act on the table as a whole (column visibility, filters, bulk operations) rather than on a single row. Prefer placing a single Menu trigger inside TableCellActions when you have more than two or three actions, so you do not crowd the row with icons. If an action must always be discoverable — for example a high-frequency primary action — put it in its own TableCell instead of hiding it behind row hover. TableCellActions is also unnecessary in tables where rows are not editable or actionable, since hidden controls add noise and DOM weight for no benefit.

## Best Practices

### Do's

- Render TableCellActions as the last cell of each TableRow so hover-revealed controls land at a predictable trailing edge.
- Give every icon-only control inside the component a descriptive aria-label (for example "Edit row" or "Delete row") so each action is announced individually.
- Use the visible prop set to true whenever a Popover, Menu, or Dialog opened from these actions is still mounted, so the actions do not disappear mid-interaction.
- Keep the control count to one or two direct buttons plus an overflow Menu; more than that becomes hard to scan at row hover speed.
- Pair TableCellActions with TableCellLayout in the preceding cell so the row's content and its actions stay visually balanced.
- Verify the actions remain reachable and visible when the row is focused via keyboard, not only on pointer hover.

### Don'ts

- Do not hide the actions with display: none or visibility: hidden by default, which removes them from the tab order and makes the row's controls unreachable by keyboard.
- Do not scatter actions across multiple TableCells in the same row; grouping them in a single TableCellActions cell keeps hover and focus behavior coherent.
- Do not put the row's primary, always-needed action inside TableCellActions where it is invisible until hover.
- Do not rely on color alone (for example a red trash icon with no label) to communicate a destructive action.
- Do not stop hover/focus propagation on the cell in a way that breaks row-level hover styling on TableRow.
- Do not use TableCellActions as a general-purpose Toolbar substitute for table-wide commands.
